# GW32 网关详细需求与验收清单

文档版本：1.3；更新日期：2026-11-19；对应 nRF 应用：`gw-nrf54l15/0.3.0`、ESP `0.3.0`；统一标准：**[GW32-E2E-1.1](gateway-end-to-end-standard.md)**。本次落实三方对齐源码，保留原93条需求及18项ACC；Beacon组合掩码使用独立BFLT编号。实现与制造前置条件见[交付记录](gateway-alignment-implementation.md)，软件验证和整机验收分别记录。

本文把用户需求拆分为可实现、可联调和可验收的条目。二进制字段以 [UART 协议](../server/docs/gateway-uart-protocol.md) 为准；服务器消息字段以 [服务器协议](../server/docs/gateway-protocol.md)、[消息 Schema](../server/internal/platform/assets/message-contracts.schema.json) 和 [OpenAPI](../server/internal/platform/assets/openapi.json) 为准。端到端流程见 [对接指南](gateway-integration.md)。

ESP 主机的模块、持久化事务、网络恢复、任务和升级执行细节见 [ESP32-S3 专项需求](esp32s3-requirements.md)。

网关必须支持手机/笔记本连接 ESP32-S3 热点后在本地网页配置上联网，同时支持平台远程配置、ESP 本地及远程 OTA。专项需求现为 **182 条、50 项验收**；详见 [配网设计](esp32s3-network-provisioning.md) 与 [ESP OTA](esp32s3-ota.md)。这些功能已有源码和软件验证证据，整机与硬件仍待验收；具体缺口按统一标准登记，不能笼统写成 ESP 全部未实现。

三方专项文档：[nRF 需求](nrf54l15-requirements.md) / [开发](nrf54l15-development.md)、[ESP 需求](esp32s3-requirements.md) / [开发](esp32s3-development.md)、[平台需求](../server/docs/gateway-platform-requirements.md) / [开发](../server/docs/gateway-platform-development.md)。

## 1. 目标与职责

网关同时支持按规则采集 BLE 广播、受控连接外部 BLE 设备、对外发送 Beacon 或自定义广播、本地与平台远程配网、ESP 本地/远程 OTA，以及通过 ESP32-S3 的网络与 UART 链路升级 nRF54L15。

| 层级 | 必须承担的职责 | 当前交付 |
| --- | --- | --- |
| 服务器 | 身份与权限、目标配置、UUID 解析、连接规则、任务、事件持久化、客户投递、升级制品与结果校验 | Go 服务及 Schema 已有实现；真实网关闭环待联调 |
| ESP32-S3 | 以太网/Wi-Fi、服务器连接、配置 journal、UART 主机、两路采集合并、Flash spool、升级下载与编排 | 已加入[ESP固件源码](../firmware/esp32s3/README.md)及平台配网扩展；目标/实板验证按独立记录判定 |
| nRF54L15 | 扫描/过滤、原始观测、Central/GATT、对外广播、Peripheral、不透明数据转发、UART DFU | C 源码、板定义、主机测试和参考工具；目标编译及实板验证未完成 |
| 手机/其他 BLE 客户端 | 发现网关、按授权业务写入 RX、订阅 TX、业务级应答 | 固定 GATT、独立业务Security2、PG分片及业务ACK已实现；实际手机客户端须按协议联调 |

服务器不直接操作 nRF 串口；nRF 不直接联网。ESP 同时扫描时，跨芯片重复观测在 ESP 合并；服务器依据原始数据解析 UUID、应用授权规则并创建连接任务。

## 2. 状态与优先级约定

需求表中的状态不是整机完成度：

- **代码**：仓库存在对应实现，主机测试见验证记录；不代表目标编译或实板通过。
- **服务端**：服务端契约与校验/处理已实现；设备动作还需要 ESP 执行。
- **Cxx**：统一标准的对齐项目索引；本轮对应源码已实现，软件测试及硬件验收边界见交付记录。
- **待实测**：必须使用目标 SDK、匹配硬件和真实链路验证。
- **后续**：超出当前 0.3.0 能力；不得向服务器登记为已支持。

优先级：**P0** 为基础联调、安全和可靠控制的前置条件；**P1** 为本次要求的业务与运维功能，同样属于交付范围，按设备配置启用并完整验收；**P2** 为后续扩展。尚未实现或未通过验收的 P1 功能必须关闭相应能力声明，而不是接受后无动作。

## 4. UART 可靠控制要求

| 编号 | 优先级 | 要求 | 实现/验收边界 |
| --- | --- | --- | --- |
| UART-001 | P0 | 使用 COBS 分隔与 CRC32C，长度/magic/版本/会话校验全部通过才分派 | nRF 代码；坏帧不得执行命令 |
| UART-002 | P0 | 上电和断链后 HELLO 建链，区分 UART 重握手和 nRF 真正重启 | nRF 代码；ESP 恢复持久状态后再接收数据 |
| UART-003 | P0 | 一次仅一个控制请求；超时重发同 ID 同内容；内容冲突不能执行 | nRF 最近请求响应缓存、ESP 单请求/重试已有代码；实板待测 |
| UART-004 | P0 | 普通命令等待 500 ms；DFU 擦写/整镜像校验等待 30 s；BUSY 退避后使用新 ID | 代码与探针；不可用新 ID 盲重试有副作用动作 |
| UART-005 | P0 | 配置以 revision 对账；相同版本相同内容幂等，相同版本不同内容冲突，更旧版本拒绝 | nRF 代码；ESP 持久保存目标及实际状态 |
| UART-006 | P0 | FIFO 批次仅在 ESP 持久接管后 CUSTODY 回收；BUSY 保留，FAULT 暂停自动发送 | 两端代码及 ESP spool 故障测试已有；真实 Flash/断电待测 |
| UART-007 | P0 | 控制与 ACK 优先，保留状态、坏帧、重试、队列和丢弃计数 | nRF 代码；CTS 阻塞恢复待实测 |
| UART-008 | P0 | nRF RAM 数据复位后可丢失；ESP 不得把 RAM 接纳或 MQTT PUBACK 当持久化完成 | 明确的故障边界；断电测试必需 |

| SCAN-006 | P0 | 16/32/128 位服务 UUID 按 AD 类型解析，保留 wireBits，归一到统一 UUID 表示 | 服务端代码；厂商 iBeacon UUID 不等于 GATT service UUID |

| SCAN-008 | P1 | 启用 ESP 扫描时，两路应用同一逻辑过滤目标并分别读回 | C10：同一双路采集任务分别配置等价目标；仍保留独立 radio 配置，参数按各控制器能力量化 |
| SCAN-009 | P2 | 扩展广播、PHY/SID 完整接收按额外能力启用 | 0.3.0 不声明完整扩展广播接收 |
| SCAN-010 | P0 | 不把 Host 解析出的 bond identity 冒充空中地址 | 当前 nRF 保守报告未知地址；相应事件不能按地址自动连接 |

## 8. 服务器控制对外广播

**广播类型分两层：** `mode` 控制是否可扫描、可连接；iBeacon、Service Data 或自定义 AD 控制内容格式。当前服务器不新增 `beaconType` 字段；通过 `advDataBase64` 和 `scanResponseBase64` 传输完整 AD，辅助生成器负责构造内容。

| 编号 | 优先级 | 要求 | 实现/验收边界 |
| --- | --- | --- | --- |
| ADV-001 | P1 | 服务器通过 CONFIGURE 开启/关闭 nRF 或具备能力的 ESP 广播 | 三方代码及C03实际状态读回、C07本机模式已实现；实际空口待验收 |
| ADV-002 | P1 | 支持 NONCONNECTABLE、SCANNABLE_NONCONNECTABLE、CONNECTABLE_SCANNABLE | nRF 代码；可连接模式额外要求 Peripheral 能力 |
| ADV-003 | P1 | 内容支持 iBeacon、16/32/128 位 Service Data 和合法自定义 AD | 原始载荷能力和 Python 生成器已实现；不是每种格式都有独立服务器表单 |
| ADV-004 | P1 | AdvData 与 ScanRsp 各不超过 31 字节；校验完整 AD，禁止不可扫描模式携带 ScanRsp | nRF/服务端；边界和畸形内容有测试 |
| ADV-005 | P1 | 广播间隔 100～10240 ms，经 UART 0.625 ms 单位编码；返回实际值 | 代码；频率约为 1000/intervalMs Hz，实际空口受调度与随机延迟影响 |
| ADV-006 | P1 | 仅改内容时在线更新，模式/间隔改变时重启；失败恢复旧配置 | nRF 代码；AD/ScanRsp 两次写入不保证空口原子切换 |
| ADV-007 | P1 | 成功后提交 revision；恢复失败进入 FAULT 并保留错误，不能报告成功 | nRF 代码；ESP 需同时核对目标和实际状态 |
| ADV-008 | P1 | 提供 GET_ADV_STATUS：目标使能、实际状态、模式、间隔、长度、错误、时间和计数 | 35 字节状态已实现 |
| ADV-009 | P1 | 广播设置与扫描设置独立；不以改广播内容隐式清除扫描目标 | 代码/服务端；角色切换由 ESP 显式编排 |
| ADV-010 | P1 | 手机连接时暂停新广播，连接回收后按当前目标恢复；关闭广播不隐式断开手机 | nRF 代码；需要断开时显式发 0x0F |
| ADV-011 | P1 | nRF 重启默认不广播，ESP 按持久目标和最新授权恢复；UART 重握手保留本次启动配置 | 两端恢复代码；实际状态与完整目标恢复边界见 C03/C08 |
| ADV-012 | P1 | iBeacon measured power 是 1 m 校准 RSSI，不能当发射功率 | 生成器已区分；当前没有服务器可调 RF 发射功率字段 |
| ADV-013 | P2 | 多广播集、周期广播、扩展广播发送和精确占空比另行定义能力 | 不属于 0.3.0 |

## 11. nRF 空中升级需求

此处 OTA 指 **服务器经网络向 ESP 交付升级制品，再由 ESP 经 UART 更新 nRF**，不是手机经 BLE 直接给 nRF DFU。

| 编号 | 优先级 | 要求 | 实现/验收边界 |
| --- | --- | --- | --- |
| OTA-001 | P1 | 使用 FIRMWARE_UPGRADE(component=NRF54) 区分网关主固件升级，未指定 component 保持旧 GATEWAY 行为 | 服务端代码 |
| OTA-002 | P1 | 校验签名 manifest、型号/硬件版本、镜像格式 MCUboot signed bin、大小及 SHA-256 | 平台、nRF 传输校验、ESP 下载/manifest 验签已有；目标 MCUboot 验签待测 |
| OTA-003 | P1 | 首次 SWD 安装匹配 MCUboot 和双槽布局，使用项目专用 ECDSA P-256 密钥 | 构建配置；没有提供发布密钥或已验签目标镜像 |
| OTA-004 | P1 | 仅写次槽，使用 swap-using-offset；运行时检查槽位、几何、容量和 trailer | nRF 代码；不能退化为覆盖运行镜像 |
| OTA-005 | P1 | BEGIN 前排空/暂停采集并关闭冲突连接；停止无线后再次确认无存活连接对象 | nRF 代码；ESP 必须先持久接管残余 FIFO |
| OTA-006 | P1 | CHUNK 连续 offset，1～1024 字节；最近相同块可重试，跳号/不同字节拒绝 | nRF 代码；accepted_offset 包含 RAM 缓冲，不是断电检查点 |
| OTA-007 | P1 | UART 重握手可在本次 nRF 启动中续传；nRF 复位后重新 BEGIN，从 0 开始 | C11已区分传输中断与FINISH后试启动；旧offset不跨boot复用，新授权任务从0 BEGIN |
| OTA-008 | P1 | FINISH 刷新缓冲、读回整个传输文件 SHA、设置 TEST；MCUboot 启动时独立验签 | nRF 代码；SHA 正确不等于数字签名可信 |
| OTA-009 | P1 | REBOOT 延迟回复后重启；重新 HELLO 确认启动、健康及预期版本 | nRF 代码；ESP 不能把 REBOOT 返回 OK 当升级成功 |
| OTA-010 | P1 | VERIFY_RUNNING 核对当前主镜像 SHA 后才允许 CONFIRM；每次 nRF 重启重新验证 | nRF 代码；防止同版本字符串或回滚误报 |
| OTA-011 | P1 | 未确认试运行默认 120 s；逾期 CONFIRM 为 STALE；运行中主循环超时复位 | C04已实现有限重握手和持久意图后的单次硬件复位；板级复位默认关闭，脉冲/回退待实测 |
| OTA-012 | P1 | 成功结果须含 NRF54 component、版本、nrfBootId、bootConfirmed=true、匹配制品的 imageSha256 | 服务端校验；不能覆盖 ESP 主固件版本字段 |
| OTA-013 | P1 | 活跃升级期间阻止业务配置冲突；ABORT 清理次槽并按目标恢复无线 | nRF 代码；READY 后仍需显式重启或终止 |
| OTA-014 | P1 | 私钥离线管理，仓库不存生产密钥；制品发布有权限、审计与兼容约束 | 构建脚本拒绝 SDK 默认示例私钥；密钥运维待部署 |
| OTA-015 | P2 | 硬件强制防降级、密钥轮换、断电跨启动续传、bootloader 自升级另行设计 | 当前不宣称这些能力；MCUboot 回退不等于安全版本防降级 |

NRF54与GATEWAY使用独立组件库存，按一次性挑战、世代和运行镜像证据登记；证据不足为VERSION_ONLY或UNKNOWN。指定 `fromFirmwareVersions` 的 NRF54 制品仍要求可信独立来源，不拿 ESP 版本代替。详见服务器协议和C06实现。
