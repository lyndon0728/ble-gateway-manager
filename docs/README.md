## 后续文档格式

按用户要求，**后续新增和更新的项目需求、开发设计、接口说明、测试计划/记录、发布说明和决策记录均使用Markdown（`.md`）作为维护源文件**。使用UTF-8、仓库约定的LF换行，文件名稳定，中文正文配合准确的字段/API名称。

图表优先使用Markdown表格、Mermaid或附带明确说明的图片。机器可执行的Schema、构建配置、分区表、源码、测试数据和原始仪器证据保持其必要原生格式，由Markdown解释和引用。既有历史文件保留，本规则不自动触发历史格式转换或删除。

## 内容与变更规则

1. 每份文档写明日期、版本、依据与状态：设计、已实现、已测试分别描述。
2. 保持已有系统需求及 `ACC-*`、`ESP-*`/`ESP-AT-*` 编号；nRF专项映射原系统编号，平台专项使用其独立编号。已有编号不重复分配或因排序改变。
3. 开发函数名/目录若尚不存在，标注“计划接口/计划目录”；构建命令给出前提，不能把未执行命令写为成功记录。
4. 外部协议变化须同步两层协议、Schema和实现，再更新需求、设计与验证映射；内部状态不得直接变成新线上字段。
5. 用相对路径连接仓库内资料；使用官方来源链接核对外部API，并记录SDK版本。不要只引用本机绝对路径作为可交付依据。
6. 记录实际测试命令、提交号、SDK/板版本、输入、预期、实际、证据和限制。主机替身通过不等于目标编译、射频或整机OTA通过。
7. 检查相对链接、代码块、编号唯一性、需求与用例覆盖以及`git diff --check`；不要伪造测试日期或通过状态。
8. 源码未实现、接口未冻结、硬件未连接等情况明确标记；公开文档和示例不包含token、密码或私钥。

## Markdown记录模板

以下模板仅用于之后实际发生的设计决策或测试，不是已经执行的记录。

```markdown
# 记录标题

| 项目 | 内容 |
| --- | --- |
| 日期 / 文档版本 | 实际日期 / 版本 |
| 关联需求 / 用例 | ESP-... / ESP-AT-... |
| 源码提交 / SDK / 板版本 | 实际标识；未知写未确认 |
| 状态 | 设计 / 未执行 / 通过 / 失败 / 阻塞 |

## 输入与前置条件

记录配置、设备、数据及授权范围。

## 方案或执行步骤

列出决定或实际执行内容。

## 结果与证据

分别写预期、实际及仓库相对证据链接；未执行不得填写通过。

## 限制与后续动作

说明未解决项、责任模块及影响。
```
